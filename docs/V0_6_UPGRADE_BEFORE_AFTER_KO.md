# v0.6 고도화 전후 비교 및 개발 결과

> 기준: v0.5.3 (`2ba72a0`) → v0.6.0  
> 근거 계획: [10월 2일 미팅 피드백 기반 고도화 개발 계획](MEETING_FEEDBACK_DEVELOPMENT_PLAN_KO.md)  
> 개발일: 2026-10-05

## 1. 이번 개발의 목표

기능 수를 늘리는 대신, 검사 결과가 **어떤 화면·음성·시간 조건에서 만들어졌는지 재현할 수 있게** 만드는 것이 목표였다. 특히 회의에서 지적된 다음 문제를 우선 해결했다.

- “350ms”가 코드 설정일 뿐 실제 제시시간인지 알 수 없었다.
- TTS 음성과 속도가 기기마다 달랐지만 사용 조건이 충분히 남지 않았다.
- UI의 글꼴·크기·행간이 코드 여러 곳에 있고 검사 사양 버전이 없었다.
- 제시 실패가 오답과 구분되지 않을 위험이 있었다.
- ASR 도입 근거를 설명할 CER/WER·속도 계산 절차가 없었다.
- 본검사 무피드백 원칙이 코드 구조에만 의존하고 독립 테스트가 없었다.

| 품질 실패 점수 | 별도 제외 규칙 없음 | 제시 실패와 음성 실패를 점수 0과 분리 |

| 데이터 형식 | `schemaVersion 0.2/0.3` | 신규 세션 `schemaVersion 0.4`, 과거 기록 자동 보완 |

## 3. 구현 상세

### 3.1 검사 사양 중앙화

새 파일 `assessment-spec.js`에 다음을 모았다.

- 단어·지문·선택형 자극의 글꼴, 크기, 굵기, 자간, 행간, 최대 폭
- 전경·배경색
- 자극 노출 허용 오차와 무효 상태
- TTS 언어, 속도, pitch, volume, timeout, 음성 선택 정책
- 실행 환경 스냅샷, TTS WPM 추정, 제시 품질 요약 함수

CSS는 이 사양이 주입하는 변수로 자극 모양을 결정한다. 앞으로 글꼴이나 크기를 바꾸면 사양 버전도 함께 올려 세션 간 조건이 섞이지 않게 할 수 있다.

### 3.2 자극시간 실측과 무효 처리

단어 재인 과제는 다음 순서로 동작한다.

1. 문항 DOM을 만든다.
2. `requestAnimationFrame`으로 첫 paint 경계를 잡는다.
3. 그 시점의 `performance.now()`를 반응시간·노출시간 시작점으로 쓴다.
4. 목표 350ms 뒤 마스킹하고 실제 경과시간을 측정한다.
5. 실제 노출이 410ms를 초과하면 `PRESENTATION_INVALID`로 기록한다.
6. 응답·정답 여부·반응시간은 근거 추적을 위해 남기되 점수 집계에서는 제외한다.

참여자가 350ms 전에 응답한 경우에는 이미 판단을 마친 것이므로 조기 종료를 무효로 보지 않는다. +60ms 허용 오차는 공학 초기값이며 저사양 기기 파일럿 후 조정해야 한다.

### 3.3 TTS와 지시문

세션에서 처음 선택된 한국어 음성을 이후에도 찾도록 고정하고 다음을 기록한다.

- 브라우저 음성 합성 엔진
- voice name, language, local/default 여부
- rate, pitch, volume
- 재생 시작·종료, 실제 재생시간
- 텍스트 길이와 추정 WPM
- 실패 코드와 사용 맥락(안내·소리 확인·문항·이야기)

듣기 문항은 음성 재생 중 선택지를 잠근다. 재생 실패 시 오류 안내를 보여주고, 다시 듣기가 성공하기 전까지 응답을 저장하지 않는다.

다만 이 개선은 **한 세션 안의 일관성**을 높인 것이다. 서로 다른 기기에 동일한 음성 파형을 보장하지는 못한다. 고정 음성 파일 또는 검증된 고정 TTS 엔진 선정은 실제 후보 비교 후 해야 한다.

### 3.4 본검사 피드백 정책

정오 문구를 만드는 `practiceFeedback`은 `practice=false`일 때 항상 `null`을 반환한다. 본검사 응답은 선택 버튼을 잠그고 즉시 다음 문항으로 이동하며 정답, 오답, 정답 선택지를 노출하지 않는다.

### 3.5 ASR 검증 준비

`scoring.js`에 다음 계산을 추가했다.

- 사람 축어 전사 대비 CER
- 사람 축어 전사 대비 WER
- 사람 정오와 자동 정오의 일치율·Cohen's κ
- 분석시간 ÷ 음성길이(real-time factor)

`node tools/asr_benchmark.mjs <benchmark.json>`으로 계산할 수 있다. [실제 음성 ASR 검증 절차](ASR_VALIDATION_PROTOCOL_KO.md)에 필요한 녹음 조건과 입력 형식을 적었다.

실제 녹음 기준 자료가 없으므로 이번 개발에서 정확도 수치를 만들지 않았다. 결과지의 성능값은 실제 자료가 들어올 때까지 확정할 수 없다.

## 4. 데이터 변화

새 세션에는 다음 필드가 추가된다.

```text
appVersion
assessmentSpecVersion
environment
  ├─ viewport / screen / devicePixelRatio
  ├─ webgpu / online
  └─ userAgent / platform / language
ttsProfile
ttsEvents[]
presentationLog[]
choiceAnswers[].scoringStatus
choiceAnswers[].presentation
```

과거 세션은 삭제하지 않는다. 불러올 때 `legacy-unrecorded` 사양으로 표시하고 없는 배열만 보완한다.

## 5. 결과지 변화

전문 결과지의 검사 품질 영역과 선택형 결과지에 다음이 표시된다.

- 검사 사양 버전
- viewport·DPR·scale
- WebGPU와 온라인 상태
- 사용 TTS 음성과 속도
- TTS 재생·실패 횟수와 WPM 중앙값
- 시간 계측 문항 수, 최대 지연, 점수 제외 문항 수

문항별 근거 추적 표에는 각 응답이 유효한지, 실제 노출시간이 얼마인지, 왜 제외되었는지가 나타난다.

## 6. 자동 검증 결과

`npm run check`로 다음을 확인했다.

- 전체 JavaScript 구문 검사
- classic script 결합 시 전역 이름 충돌 검사
- 화면 템플릿·저장·녹음·채점 연결 smoke test
- 검사 사양 버전과 시각 토큰
- 350ms 노출의 정상·경계·초과·조기응답 판정
- 세션 음성 선택 고정 정책
- 연습/본검사 피드백 분리
- 품질 실패 응답의 점수 제외
- ASR CER/WER·일치도·처리속도 계산
- 기존 해독·유창성·선별·선택형 채점 테스트
- 문항 발음·조건·균형 점검

전체 자동 검사가 통과했다.

로컬 브라우저 UI 직접 점검은 실행 환경에서 `localhost` 브라우저 접근 권한이 거부되어 수행하지 못했다. 따라서 실제 Chrome/Edge에서의 음성 목록, 음성 재생, 마이크 권한, 화면 paint 편차는 아래 수동 기기 점검으로 남는다.

## 7. 아직 끝나지 않은 실증 작업

| 항목 | 남은 이유 | 다음 완료 조건 |
|---|---|---|
| 고정 TTS 선정 | 후보 음질·속도·비용·개인정보 비교 자료 없음 | 같은 문장 세트로 후보별 WPM·지연·명료도 비교 후 엔진/음성 확정 |
| 실제 ASR 성능 | 실제 한국어 개발용 녹음 없음 | 내부 비식별 녹음 → 사람 축어 전사 → CER/WER·κ·RTF 표 생성 |
| +60ms 허용 오차 | 공학 초기값 | Windows/macOS, 정상/저사양 기기 분포로 조정 |
| 폰트·행간 근거 | 사양은 중앙화했지만 사용자·문헌 검증 전 | 대상 연령별 가독성 문헌 확인과 인지 인터뷰 |
| 비계 L1/L2 | 동형 후보가 없어 같은 문항 반복 시 기억 효과 | D 경로 동형 후보 제작·검토 후 조건 순서 균형화 |
| CAT | 문항은행·IRT·규준 없음 | P2 조건 충족 후 별도 연구로 시작 |

## 8. 수동 확인 체크리스트

- [ ] Windows Chrome에서 한국어 음성명·속도·재생시간 저장
- [ ] Windows Edge에서 같은 절차 반복
- [ ] macOS Chrome/Safari 후보에서 음성 차이 확인
- [ ] 음성 재생 실패 시 선택지가 잠겨 있는지 확인
- [ ] 단어 재인 문항의 `actualMs`, `driftMs` 확인

- [ ] 결과지 기술 사양표와 문항별 품질 상태 확인
