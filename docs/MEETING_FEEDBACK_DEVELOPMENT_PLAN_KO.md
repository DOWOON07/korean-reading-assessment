# 10월 2일 미팅 피드백 기반 고도화 개발 계획

> 문서 성격: 2026-10-02 가현욱 교수님 미팅 회의록을 현재 v0.5.3 코드와 대조해 만든 개발 기준서  
> 작성일: 2026-10-05  
> 적용 대상: 한국어 디지털 읽기평가 연구용 프로토타입  
> 주의: 회의록의 제품명·수치·학술 용어는 자동 전사 오류가 있을 수 있다. 구현 근거로 채택하기 전에 원자료와 문헌을 다시 확인한다.

## 1. 결론부터: 지금 우리가 만드는 것

우리가 만드는 것은 **기존 읽기검사를 화면으로 옮긴 온라인 문제지**가 아니다.

현재 프로젝트의 목표는 다음 세 층을 하나의 연구용 시스템으로 만드는 것이다.

1. **읽기 수행 측정**: 해독, 낭독 유창성, 언어 이해, 글 이해를 같은 디지털 절차로 실시한다.
2. **과정 데이터 수집**: 정오뿐 아니라 음성, 반응 시작, 읽기 시간, 오류 위치, 자기수정, 재청취, 도움 사용을 남긴다.
3. **검사자가 다시 확인할 수 있는 자동화**: ASR/STT가 초벌 전사와 오류 후보를 만들고, 사람이 원음성과 나란히 비교해 확정한다.

이 프로젝트가 메우려는 고리는 **전문가가 매번 현장에서 듣고 수기로 채점해야 하는 읽기평가를 디지털로 실시·기록·검토할 수 있게 하는 것**이다. 여기에 디지털에서만 가능한 비계 제공 전후 비교를 더하면, 단순 원점수뿐 아니라 “어떤 지원이 있을 때 수행이 달라지는가”까지 탐색할 수 있다.

따라서 현재의 올바른 정체성은 다음과 같다.

> **사람이 검증할 수 있는 ASR 보조 자동채점과 통제된 자극 제시를 갖춘 한국어 읽기 수행·동적평가 연구 플랫폼**

아직은 진단 도구가 아니다. 문항 타당화, 대표 표본 규준, 임상적 기준점이 없으므로 난독증 여부, 표준점수, 백분위, 위험군을 확정하면 안 된다.

## 2. 미팅에서 확정된 방향

### 2.1 STT/ASR은 빼지 않는다

다른 디지털 검사가 STT를 쓰지 않는다는 사실만으로 이 프로젝트에서도 제외하면 안 된다. STT는 이 프로젝트가 현장 수기 채점과 달라지는 핵심 기술이다. 다만 자동 결과를 정답으로 간주하지 않고 다음 안전장치를 둔다.

- 원음성, 원문, ASR 전사, 오류 후보를 함께 제시한다.
- 검사자가 틀린 구간을 재생하고 수정할 수 있게 한다.
- 모델명, 실행 장치, 처리 시간, 음질 상태를 기록한다.
- 실제 한국어 음성에 대한 정확도와 사람 채점 일치도를 별도로 보고한다.
- ASR 신뢰도가 낮거나 음질이 나쁘면 자동 확정하지 않는다.

현재 코드에는 원음성 재생, ASR 전사, 어절 정렬, 사람 전사, A/B 채점, Cohen's κ가 이미 있다. 다음 단계는 기능 추가보다 **실제 음성에서 이 방어벽이 제대로 작동함을 입증하는 것**이다.

### 2.2 새로운 범위를 넓히기보다 측정 조건을 정교하게 만든다

교수님 피드백의 중심은 “왜 이 폰트인가, 왜 이 크기인가, 왜 이 속도인가, 실제 제시 시간은 맞는가”에 답할 수 있어야 한다는 것이다. 이제부터 UI 값 하나도 장식이 아니라 측정 조건이다.

관리해야 할 조건은 최소한 다음과 같다.

- TTS 엔진·음성·말하기 속도·실측 WPM·음량
- 글꼴·크기·굵기·행간·행 길이·대비·배경색
- 화면 크기·픽셀 밀도·브라우저 배율·권장 시청 거리
- 자극 노출 목표 시간과 실제 노출 시간
- 반응시간 측정 기준점
- 네트워크·모델 로딩·렌더링 지연
- 마이크·샘플레이트·클리핑·무음·잡음 상태

이 값들은 코드에 흩어진 상수가 아니라 버전이 있는 검사 사양으로 모으고, 세션마다 실제 적용값과 편차를 저장해야 한다.

### 2.3 비계는 “힌트”가 아니라 별도 실험 조건이다

읽기 어려움이 있는 참여자에게 핵심 구절 강조, 문장 분절, 재청취 같은 지원을 제공하고 전후 수행 차이를 보는 것은 종이 검사보다 디지털 시스템이 잘할 수 있는 부분이다. 이것이 프로젝트의 연구 기여가 될 수 있다.

그러나 비계를 기본검사 점수에 섞으면 안 된다.

- `L0`: 도움 없는 기준 수행
- `L1`: 시각적 주의 단서(핵심 구절 강조 등)
- `L2`: 구조화 지원(문장 분절, 단계별 제시, 제한적 재청취 등)

각 조건은 별도 점수로 저장하고 `지원 후 점수 - 무도움 점수`를 탐색적 반응성 지표로만 본다. 같은 문항을 반복하면 기억 효과가 생기므로 동형 후보 문항과 조건 순서 균형화가 필요하다. 이 값도 규준이나 진단 기준으로 부르지 않는다.

### 2.4 CAT는 지금 구현할 기능이 아니라 미래 확장점이다

컴퓨터 적응검사(CAT)는 아이디어만으로 구현할 수 없다. 최소한 다음이 필요하다.

- 충분한 크기의 문항은행
- 문항별 난이도·변별도 등 IRT 모수
- 측정하려는 능력 차원의 정의
- 대상 연령·집단별 보정과 표준화 자료
- 중단 규칙과 오차 기준

현재 조건에서 난이도를 임의로 올리고 내리는 기능은 “CAT”라고 부를 수 없다. 지금은 향후 교체 가능한 문항 선택 인터페이스와 데이터 구조만 고려하고, 실제 적응형 출제는 보류한다.

### 2.5 본검사 중 즉시 정오 피드백은 주지 않는다

오답 직후 “틀렸어요”를 보여주면 다음 문항 수행, 불안, 동기에 영향을 줄 수 있다. 현재 코드는 연습 문항에만 정오 피드백을 주고 본검사에서는 바로 다음 문항으로 넘어간다. 이 원칙을 자동 테스트로 고정하고, 연습/본검사 표시를 더 분명히 한다.

### 2.6 지시문 자체가 읽기 부담이 되지 않게 한다

읽기 능력을 측정하면서 지시문을 읽어야만 과제를 이해할 수 있게 하면 구인이 섞인다. 모든 핵심 지시문은 다음 방식으로 제공한다.

- 짧고 일관된 쉬운 문장
- 화면 텍스트와 음성 안내 동시 제공
- 연습 문항으로 이해 여부 확인
- 검사자가 다시 설명했는지 기록
- 음성 안내 실패 시 본검사 진입 차단 또는 경고

## 4. 개발 원칙

### 원칙 1. 기준 수행과 지원 수행을 분리한다

무도움 수행은 비교 가능한 측정값이고, 비계 수행은 도움에 대한 반응이다. 두 값을 합치거나 더 높은 값을 최종점수로 대체하지 않는다.

### 원칙 2. 목표값과 실측값을 모두 저장한다

예를 들어 노출시간은 `targetExposureMs: 350`만 저장해서는 부족하다. `actualExposureMs`, `driftMs`, `renderReadyAt`, `invalidReason`을 함께 남긴다.

### 원칙 3. 자동화는 근거를 숨기지 않는다

자동 점수마다 모델 버전, 원 전사, 정렬 결과, 신뢰 신호, 사람 수정 이력이 연결되어야 한다. 사람이 수정한 뒤에도 자동 원본을 보존한다.

### 원칙 4. 연구 모드와 운영 모드를 구분한다

개발 중에는 상세 로그와 비교 화면을 켜고, 참여자 화면에는 수행을 방해하는 정보가 나타나지 않게 한다. 검사자용 정보와 참여자용 정보를 같은 화면에 섞지 않는다.

### 원칙 5. 검증되지 않은 기능 이름을 과장하지 않는다

- 임의 난이도 분기 → CAT라고 부르지 않음
- 도움 후 향상 → 치료 효과라고 부르지 않음
- 자동 전사 일치 → 진단 정확도라고 부르지 않음
- 소수 팀원 테스트 → 표준화라고 부르지 않음

## 5. 목표 구조

```text
검사 사양(spec)
  ├─ 자극 표시 규격
  ├─ TTS/음성 규격
  ├─ 시간·반응 측정 규격
  └─ 허용 오차·무효 기준
          ↓
준비 단계(preflight)
  ├─ 화면·배율·오디오·마이크 확인
  ├─ 모델·음성·문항 자산 사전 로드
  └─ 준비 실패 시 본검사 차단/경고
          ↓
실시 엔진
  ├─ L0 기준 검사
  ├─ 선택적 L1/L2 비계 조건
  └─ 목표값 + 실측값 + 상호작용 로그
          ↓
분석
  ├─ ASR 초벌 전사와 정렬
  ├─ 사람 이중 확인
  ├─ 기준 수행과 지원 반응 분리
  └─ 품질 조건을 통과한 자료만 집계
          ↓
재현 가능한 결과지·기술 사양표
```

## 6. 우선순위별 구현 백로그

### P0 — 다음 고도화에서 반드시 할 것

#### P0-1. 검사 사양 레지스트리 만들기

새 파일 후보: `assessment-spec.js`

포함할 값:

- 사양 버전
- 자극 유형별 글꼴, 크기, 행간, 최대 행 길이, 대비
- TTS 음성 ID, 목표 속도, 실측 WPM 허용 범위
- 문항별 목표 노출시간과 허용 편차
- 반응시간 시작·종료 정의
- 화면/오디오/마이크 사전 점검 기준

완료 기준:

- 검사 화면의 측정 관련 상수가 사양 파일에서 나온다.
- 결과 JSON과 결과지에 사양 버전이 남는다.
- 한 장짜리 기술 사양표를 코드에서 생성할 수 있다.

#### P0-2. 자극 제시 정확성 계측

대상: `app.js`, `battery.js`, 새 `presentation-timing.js` 후보

구현:

- 다음 문항 DOM과 필요한 음성을 미리 준비한다.
- `performance.now()` 기준으로 표시 시작·마스킹 완료 시각을 기록한다.
- 목표 대비 지연을 세션에 저장한다.
- 허용 편차를 넘은 문항은 `PRESENTATION_INVALID`로 표시한다.
- CPU 부하를 인위적으로 준 회귀 테스트를 만든다.

완료 기준:

- 350ms 과제에서 목표값과 실제값을 문항별로 확인할 수 있다.
- 지연된 문항이 정상 반응시간 자료로 섞이지 않는다.
- 네트워크가 끊겨도 이미 시작한 하위검사의 자극 자산이 준비되어 있다.

#### P0-3. TTS/음성 표준화

구현 전에 최소 두 후보를 비교한다. 회의록에 언급된 특정 제품·버전은 전사 오류 가능성이 있으므로 별도 확인한다.

평가 항목:

- 한국어 자연스러움과 명료도
- 목표 연령에서 이해 가능한 속도
- 음성별 실측 WPM과 문장 간 편차
- 첫 재생 지연과 전체 재생 시간
- 오프라인/온라인 의존성
- 개인정보, 비용, 재현성, 라이선스

완료 기준:

- 본검사에서 기기 기본 음성이 임의로 선택되지 않는다.
- 사용 음성의 ID·엔진·속도·실측 길이가 세션에 기록된다.
- 재생 실패나 과도한 지연이 있으면 해당 문항을 시작하지 않는다.

#### P0-4. 지시문 접근성 통일

완료 기준:

- 모든 핵심 하위검사 안내에 동일한 “듣기” 동작이 있다.
- 텍스트와 음성 내용이 같은 버전으로 관리된다.
- 연습 문항 전에는 안내 재생이 끝났는지 확인한다.
- 재생 횟수와 검사자 추가 설명 여부가 저장된다.

#### P0-5. 실제 음성 ASR 기준선 만들기

윤리 승인 전에는 연구 참여자 자료가 아니라 팀 내부의 비식별 개발용 녹음으로만 실시한다.

최소 자료:

- 표준적으로 읽은 실제단어·비단어
- 의도적 대치·생략·삽입·반복·자기수정
- 빠른/느린 낭독
- 낮은 음량, 배경 소음, 마이크 거리 변화

보고 지표:

- 문자 오류율(CER), 단어 오류율(WER)
- 해독 문항 정오 일치율
- 유창성 오류 사건별 precision/recall
- 사람 판정과 자동 판정의 일치율·κ
- 음성 길이 대비 처리시간(real-time factor)
- 장치·브라우저별 실패율

완료 기준:

- “ASR을 얼마나 믿어야 하는가”를 표로 답할 수 있다.
- 자동 확정이 위험한 조건을 명시하고 시스템 경고와 연결한다.

#### P0-6. 본검사 무피드백과 실패 경로 테스트

추가할 자동 테스트:

- 연습에만 정오 피드백이 표시된다.
- 본검사 응답 후 정답·오답·정답 선택지가 노출되지 않는다.
- TTS 실패, 자극 지연, ASR 실패가 점수 0으로 저장되지 않는다.
- 검사 중 새로고침·중단 시 불완전 상태가 보존된다.

### P1 — P0 안정화 후 만들 연구 기여

#### P1-1. D 경로 비계 실험 모드

첫 적용은 글 이해 경로로 제한한다.

- L0: 원문과 질문만 제시
- L1: 질문과 관련된 문장에 시각적 주의 단서
- L2: 관련 문장 분절 + 음성 재생 또는 단계적 질문

저장 예시:

```json
{
  "supportCondition": "L1_VISUAL_CUE",
  "baselineItemId": "D-INF-03A",
  "parallelItemId": "D-INF-03B",
  "conditionOrder": "L0_THEN_L1",
  "baselineCorrect": false,
  "supportedCorrect": true,
  "baselineRtMs": 8200,
  "supportedRtMs": 6100,
  "supportEvents": [{ "type": "HIGHLIGHT_SHOWN", "atMs": 0 }]
}
```

완료 기준:

- 기준 점수와 비계 점수가 별도 표시된다.
- 비계 결과가 규준 점수나 전체 점수를 덮어쓰지 않는다.
- 동형 후보와 순서 균형화 없이는 정식 연구 결과로 내보내지 않는다.

#### P1-2. 결과지에 품질·지원 반응 층 추가

- 검사 사양 준수율
- 지연/음질/ASR 실패 문항 수
- ASR 모델별 검증 성능
- L0와 지원 조건의 변화량
- 해석 가능한 범위와 금지된 해석

### P2 — 데이터가 쌓인 뒤에만 시작

- 전문가 문항 검토와 인지 인터뷰
- 예비검사 기반 문항 난이도·변별도 분석
- 동형검사 구성
- 연령·집단별 대표 표본 설계
- IRT 문항은행
- CAT 시뮬레이션과 중단 규칙
- 임상·교육 현장 타당도 연구

## 7. 다음 개발 스프린트 제안

### 스프린트 목표

> “검사가 어떤 조건으로 제시되었는지 재현할 수 있고, 시간·음성 실패가 점수에 섞이지 않는 버전”을 만든다.

### 작업 순서

1. `assessment-spec.js`와 사양 버전 도입
2. 세션 JSON에 환경·사양·실측 제시값 저장
3. 350ms 자극 사전 준비와 실제 노출시간 계측
4. 본검사 무피드백 자동 테스트
5. 공통 음성 지시문 컴포넌트
6. TTS 후보 벤치마크용 개발 화면과 기록 형식
7. 내부 실제 음성 ASR 벤치마크 절차 작성
8. 기술 사양표와 결과지 품질 요약 연결

### 스프린트 종료 시 시연해야 할 장면

- 같은 문항을 두 기기에서 실행하고 적용된 사양과 실제 제시시간 비교
- 의도적으로 렌더링 지연을 발생시켜 문항이 무효 처리되는 모습
- TTS 엔진·음성·WPM·재생 지연이 결과 JSON에 남는 모습
- ASR 오류 구간을 원음성과 원문으로 확인하고 사람이 수정하는 모습
- 연습에서는 피드백이 나오고 본검사에서는 나오지 않는 모습

## 10. 완료 정의

다음 질문에 증거로 답할 수 있어야 이번 고도화가 끝난다.

1. 왜 이 글꼴, 크기, 행간, 폭을 사용했는가?
2. 목표 350ms가 실제로 몇 ms 제시되었는가?
3. 어떤 TTS 음성이 몇 WPM으로 재생되었는가?
4. 지시문을 읽기 어려운 참여자도 과제를 이해할 수 있는가?
5. 본검사 중 정오 피드백이 수행에 영향을 주지 않는가?
6. ASR이 놓친 것과 참여자가 실제로 틀린 것을 어떻게 구분하는가?
7. 자동채점을 어느 조건에서 얼마나 신뢰할 수 있는가?
8. 지원 없이 한 수행과 비계를 받은 수행이 분리되어 있는가?
9. 네트워크나 렌더링 지연이 점수로 오염되지 않는가?
10. 한 세션의 기술 조건을 나중에 그대로 설명할 수 있는가?

## 11. 당장 하지 않을 것

- 표준점수·백분위·난독증 판정
- 근거 없는 자동 난이도 조절을 CAT로 표시
- 비계 후 점수로 기준 점수 대체
- 기기 기본 TTS를 표준화 음성이라고 간주
- ASR 전사를 사람 확인 없이 gold data로 사용
- 기존 상용 검사 문항·음원을 외부 배포물에 복제
- 기능 수를 늘리기 위한 새 모듈 추가

## 12. 의사결정 요약

| 질문 | 결정 |
|---|---|
| STT를 뺄 것인가? | 아니오. 핵심 차별점으로 유지하되 검증과 사람 확인을 강화한다. |
| 외국 도구를 한국어로 그대로 옮길 것인가? | 아니오. 형식은 참고하되 한국어 읽기와 현장 문제에 맞는 독자 기여를 만든다. |
| 다음 기능은 CAT인가? | 아니오. 문항은행·IRT·규준이 생긴 뒤의 P2 과제다. |
| 지금 가장 중요한 것은? | 측정 조건, 시간 정확성, TTS, 지시문, ASR 성능의 통제와 기록이다. |
| 비계는 넣을 것인가? | 예. 기준검사와 분리한 탐색적 동적평가 조건으로 단계적으로 넣는다. |
| 결과를 진단으로 보여줄 것인가? | 아니오. 검증 전에는 원점수, 과정, 품질, 탐색적 차이만 보고한다. |
