# v0.7 업데이트 전후 비교와 검증 상태

> 기준 상태: v0.6.0 로컬 체크포인트 `b01d1d3` → v0.7.0 작업 트리  
> 작업일: 2026-10-05  
> 원칙: 이 문서는 “코드에 구현됨”과 “사람·자료로 검증됨”을 구분한다. v0.7은 아직 커밋·푸시하지 않았다.

## 1. 이번 업데이트의 결론

v0.7의 목표는 기능을 더 많이 보여주는 것이 아니라 **참여자가 검사에 집중하고, 검사자는 같은 조건으로 실시됐는지 확인할 수 있게 만드는 것**이다. A 세부검사 때 관찰된 렉은 자극 제시와 음성인식 계산이 경쟁할 수 있다는 문제로 보고, 음성인식을 모든 자극 제시가 끝난 뒤로 미뤘다. 선택형 문항은 다음 두 화면의 DOM을 유휴 시간에 미리 만든다.

교수님 피드백에서 요구한 실시·기록·검증 기능은 코드에 모두 반영했다. 이제 남은 것은 TTS 자연스러움, 글자 크기의 대상자 적합성, ASR 정확도, 문항 타당도를 실제 사람이 확인하고 자료를 채우는 일이다. 규준과 CAT는 교수님 의견대로 이번 구현 범위에 넣지 않았다.

## 3. 렉 대응의 정확한 동작

1. 검사 시작 전에 ASR 모델 준비가 끝나거나 실패 상태가 확정될 때까지 환경 확인 버튼을 잠근다. 모델 다운로드·셰이더 예열이 자극 제시와 겹치지 않게 한다.
2. 녹음형 문항에서는 음성을 IndexedDB에 저장한 뒤 다음 문항으로 이동한다. 무거운 Whisper 추론은 시작하지 않는다.
3. 모든 녹음형·선택형 자극 제시가 끝난 `complete` 화면에서 ASR을 하나씩 실행한다. 검사 중 렉을 줄이는 대신 결과 대기시간은 늘어날 수 있다.
4. 선택형 문항은 다음 두 단계의 텍스트, 보기 순서, DOM 템플릿을 `requestIdleCallback`으로 미리 만든다.
5. 350ms 자극은 두 번의 `requestAnimationFrame` 뒤 고해상도 시계를 시작한다. +60ms를 넘겨 늦게 가려지면 답은 보존하되 점수에서 제외한다.
6. 브라우저가 Long Tasks API를 지원하면 50ms 이상 메인 스레드 작업과 제시 직전 프레임 간격을 기록한다.

## 4. 글꼴·크기·배치의 근거와 한계

- 읽기 자극은 장식보다 획 구분이 쉬운 산세리프를 우선한다. Google Fonts의 Noto Sans KR 웹폰트를 고정해 불러오고 검사 전 로딩 완료를 기다리며, 불러오기 실패 시 Malgun Gothic을 대체로 기록한다. 작은 화면용 한글 글꼴 연구에서는 열린 속공간, 두꺼운 획, 낮은 획 대비, 넓은 자간이 가독성에 유리한 설계 방향으로 보고됐다.
- 한국어 글자 가독성은 연령, 시거리, 글꼴의 영향을 받으므로 화면 폭만으로 크기를 정하지 않는다. 카드 보정과 50cm 거리 확인을 추가했다. 단어 18mm, 지문 5.3mm, 보기 4.8mm는 **연구 시작값**이며 파일럿에서 수정해야 한다.
- 지문은 왼쪽 정렬, 최대 34글자 폭, 행간 1.7로 제한한다. 양끝 맞춤을 피하고 긴 행을 줄여 줄 추적 부담을 낮춘다.
- 버튼은 최소 44 CSS px 이상으로 만들어 조작 오류 가능성을 낮춘다. CSS 픽셀은 물리 mm와 같지 않으므로 검사 자극은 카드 보정값을 별도로 쓴다.
- 전경 `#172133`과 배경 `#f7f9fc`를 사양화했다. WCAG AA 4.5:1을 최소 목표로 두되 자동 대비 회귀검사는 다음 단계에서 추가한다.

근거: [한국어 글자 가독성에서 연령·거리·글꼴 효과](https://pubmed.ncbi.nlm.nih.gov/21547790/), [작은 화면용 Noto Sans CJK Korean 가독성 설계 연구](https://journal.kci.go.kr/jksci/archive/articlePdf?artiId=ART002987878), [WCAG Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [WCAG Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [WCAG Visual Presentation](https://www.w3.org/WAI/WCAG21/Understanding/visual-presentation), [WCAG Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html).

## 6. 자동으로 확인한 것과 사람이 확인할 것

`npm run check`는 다음을 자동 확인한다.

- 모든 JavaScript 문법과 classic script 전역 충돌
- 화면 템플릿, 저장·녹음·채점 상태 존재
- 앱/패키지 버전 일치
- 카드 보정 계산 범위
- 350ms 허용 오차와 점수 제외 규칙
- 고품질 TTS 음성 우선순위와 고정 음원 manifest 상태
- 연습/본검사 피드백 분리
- 채점, 신뢰구간, 문항 규칙

사람이 로컬에서 확인해야 하는 항목은 첫 화면의 시선 흐름, 모바일/노트북 배치, 카드 보정 조작감, 실제 음성 자연스러움, 마이크 권한 흐름, A 전체 검사 중 체감 렉, 결과지 인쇄 배치다.

## 7. 현재 결론

“지난 미팅 피드백이 모두 **코드에 반영됐는가**”에는 **그렇다**고 답할 수 있다. STT 사람 검증, TTS 후보 선택, 글꼴·화면·거리 통제, 렉 방어와 실측, 지시문 음성·추가 설명 기록, 본검사 무피드백, L0/L1/L2 분리, 기술 사양표까지 구현했다. CAT와 규준은 데이터 전에는 만들지 말라는 피드백을 반영해 의도적으로 보류했다.

이제 남은 것은 사용자가 직접 보고·듣고·실제 녹음을 넣어 확인하는 검증이다. 자동 검사만으로 자연스러움, 이해도, 체감 렉, 실제 ASR 정확도나 문항 동형성을 확정하지 않는다.

## 8. 사용자가 직접 확인할 항목

1. `Ctrl+F5` 후 상단과 첫 화면에 `연구용 프로토타입 v0.7.0`이 같은지 본다.
2. 첫 화면에서 참여자의 주 행동이 `검사 시작` 하나로 분명하고, A~D·결과지·검증 기능은 `검사자·연구자 도구` 안에 들어갔는지 본다.
3. 연구자 도구의 `TTS 후보 검증`에서 후보를 하나씩 듣고 자연스러움·명료도·속도 적절성을 1~5점으로 평가한 뒤 고정한다.
4. 검사 시작 → 정보 입력 → 환경 확인에서 카드 폭, 50cm 거리, 화면 배율, 시력 교정, 소리 장치가 자연스럽게 기록되는지 본다.
5. A 경로를 처음부터 끝까지 실시하면서 다음 낱말로 넘어갈 때 렉이 없는지 본다. 음성인식은 검사 중이 아니라 완료 화면에서 시작되어야 한다.
6. B 단어 자동성에서 짧은 자극이 일정하게 보이고, 지연된 문항은 결과지에서 점수 제외로 표시되는지 본다.
7. D 경로 설정에서 `L0/L1/L2 비계 반응 실험 포함`을 켜고, 무도움·핵심 문장 표시·문장 분절과 듣기가 서로 다른 문항으로 나오며 정오 피드백을 주지 않는지 본다.
8. 연구용 검증 화면에서 사람 전사·판정을 입력한 뒤 결과지에 CER·WER·RTF·일치율·κ가 나타나는지 본다.
9. 노트북·큰 모니터·모바일에서 카드 보정 뒤 자극의 물리 크기와 줄 길이가 지나치게 달라 보이지 않는지 확인한다.
10. 결과지를 인쇄/PDF로 열어 기술 사양, TTS 후보, 추가 설명 횟수, 렉 기록, 비계 결과가 잘리지 않는지 본다.
