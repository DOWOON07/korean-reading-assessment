# v0.7 설계 근거와 검증 수준

> 대상: 한국어 읽기평가 연구용 프로토타입 v0.7.0  
> 작성일: 2026-10-05  
> 목적: “왜 이렇게 만들었는가”와 “어디까지 검증됐는가”를 같은 표에서 설명한다.

## 1. 먼저 결론

v0.7의 설계 방향은 타당하다. 참여자와 연구자 기능을 분리하고, 시각·청각·기기 조건을 기록하며, 시간 자극과 무거운 음성인식 계산을 분리하고, 자동 채점을 사람 기준 자료로 검증하도록 바꿨다. 각 결정은 HCI 표준, 웹 성능 표준, 읽기평가 문헌 또는 측정학 원칙과 연결된다.

그러나 **근거가 있는 설계 원칙**과 **이 프로토타입의 특정 수치가 최적임을 입증한 것**은 다르다. 현재 근거로 말할 수 있는 범위는 다음과 같다.

- 화면 대비, 행폭 상한, 행간, 왼쪽 정렬, 44px 조작 영역에는 외부 표준 근거가 있다.
- 한국어 가독성이 연령·시거리·글꼴의 영향을 받으므로 조건을 통제해야 한다는 직접 연구 근거가 있다.
- Noto Sans KR, 50cm, 18/5.3/4.8mm, 34ch는 근거를 이용해 정한 **연구 시작값**이지 대상자 최적값으로 검증된 값은 아니다.
- Whisper large-v3-turbo는 다국어 지원과 속도/정확도 절충 때문에 합리적인 후보지만, 한국어 아동 읽기 오류 채점에 대한 검증은 아직 없다.
- L0/L1/L2는 동적평가의 단계적 도움 원칙과 맞지만, 현재 세 후보 문항의 동형성과 효과는 검증 전이다.
- 규준, 절단점, 진단, CAT는 필요한 자료가 없으므로 일부러 구현하지 않았다.

## 2. 근거 수준 표기

| 표기 | 의미 | 이 문서에서의 해석 |
|---|---|---|
| `A · 직접 근거` | 표준 또는 동료평가 연구가 같은 결정·측정에 직접 연결 | 원칙 채택의 강한 근거 |
| `B · 근거 기반 적용` | 근거의 방향은 맞지만 한국어·대상 연령·현재 과제에 맞게 변형 | 파일럿과 교차타당화 필요 |
| `C · 공학 통제` | 재현성·성능·자료 보호를 위한 설계 판단 | 로그와 장애 시험으로 검증 |
| `P · 후보값` | 합리적인 시작값이나 직접 실증 전 | 최종 기준으로 주장 금지 |

`A`도 프로토타입 전체의 타당도를 자동으로 보증하지 않는다. 표준을 따른 UI와 타당한 검사는 별도의 문제다.

## 3. HCI와 UI 설계

### 3.1 첫 화면: 참여자 행동 하나, 연구 도구는 접기

**현재 구현**

- 첫 화면에서 `검사 시작`을 유일한 주 행동으로 둔다.
- A~D 경로 시연, 결과지, 자동 채점 검증, TTS 후보 검증은 `검사자·연구자 도구` 안에 접는다.
- 오른쪽에는 검사 흐름을 3단계로만 보여 준다.

**왜 이렇게 했는가**

참여자의 과제는 내부 모델과 분석 도구를 고르는 것이 아니라 검사를 시작하는 것이다. 관련 없는 선택지를 줄이는 것은 Nielsen의 `Aesthetic and minimalist design`, 현재 위치와 진행을 알려 주는 것은 `Visibility of system status`에 해당한다. 이는 작업기억 부담과 오조작을 줄이는 HCI 원칙이다.

**검증 수준: `B + C`**

Nielsen 휴리스틱은 널리 쓰이는 점검 원칙이지만 이 특정 화면의 사용성 실험 결과는 아니다. 대상자에게 “어디를 눌러야 할지 바로 알겠는가”를 관찰해야 한다.

### 3.2 진행 단계와 상태 가시성

**현재 구현**

- 정보 → 환경 → 선별/검사 → 세부검사 → 완료의 단계 표시
- ASR 준비, 녹음, 자동 채점, TTS 재생 상태를 문장으로 표시
- 모든 화면과 결과지에 앱·문항·사양 버전을 기록

**왜 이렇게 했는가**

시스템이 무엇을 하고 있는지 알려야 사용자가 기다림과 실패를 구분할 수 있다. 버전 표시는 단순 장식이 아니라, 같은 참가자 자료가 어떤 화면·규칙·모델로 생성됐는지 추적하는 연구 재현성 장치다.

**검증 수준: `B + C`**

### 3.3 글꼴: Noto Sans KR 우선, Malgun Gothic 대체

**현재 구현**

- 읽기 자극은 `Noto Sans KR`을 웹폰트로 먼저 불러온다.
- 로딩 실패 시 `Malgun Gothic`, 그다음 sans-serif를 사용한다.
- 실제 사용 글꼴과 Noto 준비 여부를 세션·결과지에 기록한다.

**왜 산세리프인가**

Kong 등(2011)은 한국어 글자 가독성에서 연령, 시거리, 글꼴 유형이 유의한 영향을 보였고 Gothic과 Ming 조건의 차이를 보고했다. Noto Sans CJK는 한국어 글리프를 포함하고 화면·전자책·UI용으로 설계된 공개 글꼴이다. 따라서 기기 기본 글꼴이 제각각인 상태보다 한 글꼴을 먼저 고정하는 편이 재현성이 높다.

**왜 Noto Sans KR인가**

한국어 글리프 범위, 웹 배포 가능성, 여러 굵기, 운영체제 간 사용 가능성을 함께 만족하기 때문이다. 다만 “Noto Sans KR가 모든 연령의 읽기평가에서 가장 우수하다”는 직접 비교 근거는 없다. 이 선택은 글꼴을 표준화하기 위한 후보이며, 다른 고딕 글꼴과의 대상자 비교가 남아 있다.

**검증 수준: `B + P`**

### 3.4 물리 글자 크기와 카드 보정

**현재 구현**

- ISO/IEC 7810 ID-1 카드의 긴 변 85.60mm를 화면 기준자로 쓴다.
- 사용자가 맞춘 CSS px/mm로 단어 18mm, 지문 5.3mm, 보기 4.8mm를 계산한다.
- 약 50cm 시거리와 화면 배율 유지 여부를 확인하고 기록한다.

**왜 화면 폭만 쓰지 않았는가**

같은 CSS 픽셀도 화면 밀도, 운영체제 배율, 시거리에 따라 망막에 맺히는 크기가 달라진다. W3C도 CSS 픽셀을 물리 픽셀과 구분하며 시거리와 기준 시각을 고려한 단위로 설명한다. Kong 등은 한국어 글자의 가독성이 50cm와 200cm 조건에서 크게 달랐다고 보고했다. 따라서 `vw`만으로 자극 크기를 정하면 모니터가 바뀔 때 검사 조건이 달라질 수 있다.

**왜 카드인가**

일반 사용자가 자 없이도 쉽게 구할 수 있고, ISO 표준 크기가 정해진 물체이기 때문이다. 이는 화면의 물리 크기를 자동 측정할 수 없는 웹의 한계를 보완하는 사용자 보정 방식이다.

**중요한 한계**

- 50cm는 한국어 가독성 연구에 포함된 조건이라 선택했지만, 모든 대상에게 최적인 거리라는 뜻은 아니다.
- 18/5.3/4.8mm는 현재 문헌과 화면 사용성을 바탕으로 정한 시작값이다. 연령별 최적값을 직접 산출한 것이 아니다.
- 카드 맞춤은 사람의 시차와 슬라이더 조작 오차를 포함한다.

**검증 수준: 카드 규격 `A`, 보정 방식 `C`, 정확한 거리·크기 `P`**

### 3.5 행폭, 행간, 정렬

**현재 구현**

- 지문 최대 34ch, 보기 최대 42ch
- 지문 행간 1.7, 보기 행간 1.65
- 양끝 맞춤이 아닌 왼쪽 정렬

**근거**

WCAG 1.4.8은 CJK 텍스트의 폭을 40글자 이하로 만들 수 있는 수단, 1.5배 이상의 행간, 양끝 맞춤 회피를 제시한다. 현재 지문 34ch와 행간 1.7은 이 범위 안에서 줄 추적 부담을 줄이려는 보수적 선택이다.

**한계**

WCAG는 접근성 기준이지 읽기능력 측정의 규준이 아니다. 34ch가 현재 대상과 문장 구조에 최적인지는 안구 추적, 오류율, 속도, 주관적 편안함으로 확인해야 한다.

**검증 수준: 원칙 `A`, 정확한 34ch/1.7 `B + P`**

### 3.6 색 대비와 버튼 크기

**현재 구현**

- 자극 전경 `#172133`, 배경 `#f7f9fc`: 계산 대비 15.3:1
- 모든 주요 버튼·입력의 최소 높이 44 CSS px

**근거**

- WCAG 2.2의 일반 텍스트 최소 대비는 4.5:1이다. 15.3:1은 이를 넘는다.
- WCAG 2.5.5 Target Size (Enhanced)는 포인터 대상에 44×44 CSS px를 제시한다.

**한계**

강한 대비가 곧 모든 사람에게 최적의 읽기 편안함을 의미하지는 않는다. 또한 최소 높이 44px만으로 모든 버튼의 가로 크기·간격·키보드 접근성이 자동 충족되지는 않는다.

**검증 수준: `A + C`**

### 3.7 반응형 배치와 접근성

**현재 구현**

- 900px과 620px 이하에서 다열 화면을 한 열 또는 두 열로 바꾼다.
- 텍스트와 표의 폭을 제한하고 표는 필요한 경우 자체 스크롤 영역을 쓴다.
- `prefers-reduced-motion`에서 애니메이션과 전환을 끈다.
- 기본 키보드 초점을 제거하지 않는다.

**근거**

WCAG Reflow는 320 CSS px 상당의 폭에서 주요 정보와 기능을 잃지 않고 한 방향으로 읽을 수 있어야 한다고 설명한다. Focus Visible은 키보드 사용자가 현재 초점을 알아야 한다고 요구한다.

**검증 수준: `A` 원칙, `C` 구현, 전체 적합성 감사 전**

현재는 자동 접근성 감사와 실제 키보드 전수 시험을 완료하지 않았으므로 “WCAG 2.2 전체 준수”라고 표현하지 않는다.

## 4. TTS 설계

### 4.1 왜 고정 음원을 우선하는가

듣기 과제에서 목소리, 발화 속도, 억양, 휴지는 문항 난이도의 일부가 된다. 브라우저 `speechSynthesis`는 운영체제와 설치 음성에 따라 결과가 달라진다. 따라서 연구 비교에서는 검증된 같은 음원을 모든 참가자에게 주는 방식이 가장 재현성이 높다.

v0.7은 이를 위해 `tts-assets.js` manifest를 만들고 **고정 음원 → 고정한 기기 음성 → 자동 선택 기기 음성** 순서로 사용한다. 현재 manifest에는 검증 완료 음원이 없으므로 화면과 결과지에 `0개`와 기기 대체 사용을 숨기지 않고 표시한다.

**검증 수준: `C`; 고정 음원 내용은 아직 미완료**

### 4.2 왜 브라우저 TTS를 남겼는가

프로토타입을 여러 Windows 기기에서 즉시 시험하고, 후보를 비교해 연구자가 선택할 수 있게 하기 위해서다. 서버 API에 음성을 보내지 않고 별도 인증키 없이 동작한다는 장점도 있다. 반대로 기기 간 동일성을 보장할 수 없으므로 최종 표준화 엔진으로 간주하지 않는다.

### 4.3 왜 Natural/Neural 이름을 우선하는가

브라우저가 음질 점수나 합성 모델 계보를 표준 API로 제공하지 않기 때문에 음성명에 `Natural`, `Neural`, `Premium`, `Enhanced`가 포함된 후보를 먼저 보여 주는 실용적 휴리스틱이다. **이 이름은 품질 인증이 아니다.** 같은 문장으로 직접 듣고 자연스러움·명료도·속도 적절성을 평가해 고정해야 한다.

**검증 수준: `C + P`**

### 4.4 왜 0.90×와 WPM/SPM을 쓰는가

0.90×는 빠른 합성음으로 인한 이해 부담을 낮추기 위한 초기값이고, 최적값으로 검증된 수치가 아니다. 한국어는 띄어쓰기 단위만으로 실제 발화량을 충분히 설명하기 어려워 WPM과 함께 분당 한글 음절 수(SPM)를 기록한다. 한국어 명료 발화 연구도 발화율 비교에 SPM을 사용했다.

재생시간은 합성기의 `rate` 속성만 믿지 않고 실제 시작부터 종료까지 측정한다. 최종 속도는 대상 연령별 이해도와 선호도 자료로 정해야 한다.

**검증 수준: SPM 기록 `B`, 0.90× `P`**

## 5. ASR와 자동 채점 모델

### 5.1 왜 Whisper large-v3-turbo인가

Whisper는 대규모 다국어 자료로 학습된 공개 ASR 계열이다. large-v3-turbo는 large-v3의 디코더 층을 32개에서 4개로 줄인 809M 매개변수 다국어 모델로, 공식 모델 카드가 속도를 크게 높이는 대신 작은 품질 저하가 있다고 설명한다. 한국어를 지정할 수 있고, 브라우저에서 실행할 수 있는 ONNX 변환 모델이 있어 정확도 후보와 현장 속도의 절충점으로 선택했다.

**선택 순서**

1. WebGPU 가능: `onnx-community/whisper-large-v3-turbo_timestamped`
2. WebGPU 불가/실패: `whisper-small_timestamped` q8, WASM
3. 추가 실패: `whisper-base_timestamped` q8, WASM

큰 모델 하나만 강제하면 구형 기기에서 검사가 막힌다. 반대로 작은 모델만 쓰면 오류 탐지 후보의 품질을 포기할 수 있다. 따라서 장치 능력에 따른 하향 대체를 쓰고 실제 모델 ID를 결과에 남긴다.

**검증 수준: 모델 특성 `A`, 현재 한국어 읽기 채점 적합성 `P`**

공식 모델 카드도 특정 언어·도메인 배포 전에 강건한 평가를 권고한다. 따라서 Whisper 결과를 임상적 정답으로 쓰지 않는다.

### 5.2 왜 브라우저 안에서 실행하는가

- 녹음 원본을 외부 ASR 서버로 자동 전송하지 않는다.
- 네트워크 지연을 반응시간과 분리한다.
- 같은 세션 안에서 모델·장치·처리시간을 기록할 수 있다.

단, 첫 실행에는 jsDelivr의 Transformers.js와 Hugging Face 모델 가중치를 내려받는다. “완전 오프라인”이 아니라 **모델 준비 후 음성 추론이 로컬**이라는 표현이 정확하다.

**검증 수준: `C`**

### 5.3 왜 검사 중이 아니라 끝난 뒤 분석하는가

WebGPU/WASM 추론, 오디오 디코딩, DOM 렌더링이 같은 메인 환경의 자원을 경쟁하면 다음 자극이나 350ms 마스킹이 늦어질 수 있다. 미팅에서 관찰한 A 검사 렉과 직접 연결되는 위험이다.

v0.7은 다음 순서를 쓴다.

1. 환경 확인에서 모델 다운로드·초기화·1초 무음 예열
2. 검사 중에는 녹음만 IndexedDB에 저장
3. 모든 자극 제시 종료
4. 완료 화면에서 녹음을 순차 분석

검사 도중의 측정 안정성을 우선하고, 결과 대기시간이 늘어나는 비용을 선택했다.

**검증 수준: `C`; 실제 기기 부하 시험 필요**

### 5.4 왜 사람 전사와 두 채점자를 유지하는가

ASR 오류와 참가자의 읽기 오류는 같은 것이 아니다. 특히 아동 발화와 읽기 실수 탐지는 일반 음성전사보다 어렵고 언어·연령별 검증이 필요하다. 그래서 원음성, ASR 전사, 사람 축어 전사, 채점 A/B, 합의 상태를 모두 보존한다.

- CER: 문자 단위 전사 오류
- WER: 어절 단위 전사 오류
- RTF: 음성 길이에 대한 처리시간 비율
- 일치율·Cohen's κ: 자동-사람, 사람-사람의 범주 판정 일치

이 지표가 있어야 “Whisper를 썼다”가 아니라 “이 표본에서 어느 정도 맞았다”고 말할 수 있다.

**검증 수준: 지표 `A/B`, 현재 성능값은 실제 표본 전 `P`**

## 6. 시간 자극과 렉 통제

### 6.1 왜 350ms인가

ROAR의 단어 재인 과제는 실제단어/비단어를 짧게 제시하는 lexical decision 형식을 사용하며 350ms 자극 제시를 사용한다. 이 프로토타입은 빠른 단어 재인의 정확도와 반응시간을 보기 위해 그 형식을 참고했다.

그러나 영어 ROAR의 신뢰도·타당도가 한국어 문항에 그대로 이전되는 것은 아니다. 한국어 문항은행과 IRT 보정이 없으므로 현재 점수는 원점수와 실험 자료다.

**검증 수준: 형식 `A/B`, 한국어 문항과 점수 `P`**

### 6.2 왜 `performance.now()`와 두 번의 `requestAnimationFrame`인가

W3C High Resolution Time은 `performance.now()`를 시스템 시각 조정에 영향을 받지 않는 단조 증가 시계로 정의한다. 자극이 DOM에 들어간 호출 시각이 아니라 브라우저가 그리기를 준비한 프레임 경계에서 시간을 시작하려고 두 번의 `requestAnimationFrame`을 사용한다.

다음 두 화면의 DOM도 `requestIdleCallback` 시점에 미리 만들어 자극 제시 순간의 문자열 생성과 DOM 파싱 부담을 줄인다.

**검증 수준: 시계 `A`, 이중 프레임·사전 생성 `C`**

브라우저 프레임 경계는 광센서로 측정한 실제 패널 발광 시각과 같지 않다. 고정밀 실험으로 발전할 때는 외부 광센서 검증이 필요하다.

### 6.3 왜 Long Task와 +60ms를 기록하는가

W3C Long Tasks API는 50ms를 넘는 긴 작업을 보고한다. 이를 프레임 간격·실제 노출시간과 함께 남기면 “렉이 느껴졌다”를 기기·세션 자료로 바꿀 수 있다.

목표보다 60ms 넘게 늦게 가려진 문항을 무효화하는 값은 **공학 초기값**이다. 응답은 삭제하지 않고 원자료로 보존하되 점수에서 제외한다. 여러 기기의 지연 분포를 모은 뒤 허용치를 다시 정해야 한다.

**검증 수준: Long Task 기준 `A`, +60ms `P`, 보존/제외 정책 `C`**

## 7. 검사 구조와 측정 모형

### 7.1 왜 A~D 네 경로인가

읽기 결과 하나만 보여 주면 어려움의 원인을 분리하기 어렵다. 현재 구조는 다음 층을 나눈다.

- A 글자·소리/해독: 음운인식, 자모 지식, 실제·무의미단어
- B 읽기 유창성: 낭독, 단어 자동성, 문장 묵독 효율
- C 언어 이해: 어휘, 문장, 듣기, 형태소
- D 글 이해: 사실, 추론, 평가, 복수 글 비교

Simple View of Reading은 읽기이해를 해독과 언어이해의 결합으로 설명한다. 이 틀은 A/B의 인쇄물 처리와 C의 듣기 언어를 분리하고 D의 최종 글 이해와 연결하는 개념적 근거다. KOLRA, RA-RCP, BASA-R, ROAR, TOSREC, PIRLS, PISA의 과제 형식도 후보 설계에 참고했다.

**검증 수준: 개념 모형·형식 `A/B`, 현재 문항 `P`**

현재 A~D 점수만으로 난독증·특정이해결함·혼합형을 진단하지 않는다.

### 7.2 왜 연습에만 정오 피드백을 주는가

연습은 조작법과 과제 규칙을 이해하게 하는 단계라 피드백이 필요하다. 본검사에서 정답을 알려 주면 다음 문항의 전략과 수행을 바꿔 표준화 조건을 오염시킬 수 있다. ROAR의 음운인식 기술 문서도 하위검사 시작 연습 문항에 피드백을 둔다.

따라서 본검사는 응답을 수집한 뒤 다음 문항으로 이동하고, 정오를 보여 주지 않는다.

**검증 수준: `B + C`**

### 7.3 왜 L0/L1/L2를 기본 점수와 분리하는가

동적평가는 도움을 받기 전의 수행뿐 아니라 단계적 단서에 반응하는 학습 잠재력을 본다. 체계적 문헌고찰에서는 graduated prompts를 포함한 동적 읽기평가가 정적 측정 외의 설명력을 보일 가능성을 보고하지만 연구 간 차이와 추가 검증 필요성도 크다.

- L0: 도움 없는 기준 수행
- L1: 관련 핵심 문장에 시각적 주의 단서
- L2: 문장 분절과 제한적 듣기 지원

도움을 받은 점수를 기본 점수에 섞으면 서로 다른 실시 조건을 하나의 점수로 합치는 문제가 생긴다. AERA/APA/NCME Standards도 표준 조건과 수정 조건의 점수를 합칠 때 명확한 근거와 타당도·신뢰도 검토가 필요하다고 말한다. 그래서 v0.7은 조건별 자료를 별도 보존한다.

**검증 수준: 분리 원칙 `A/B`, 현재 세 문항·조건 효과 `P`**

## 8. 결과지와 보류한 기능

### 8.1 왜 기술 사양을 결과지에 같이 넣는가

점수만 있으면 다른 화면, 다른 음성, 다른 모델, 다른 지연 조건에서 생성된 자료를 구분할 수 없다. 결과지에는 다음을 같이 둔다.

- 앱·문항·채점·사양·ASR 모델 버전
- viewport, screen, DPR, visual viewport scale, WebGPU
- 카드 보정, 50cm 확인, 시력 교정, 출력 장치
- 실제 글꼴, 대비, 자극 시간 편차, 프레임 간격, Long Task 지원
- TTS 엔진·음성·속도·WPM/SPM·실패
- 추가 설명, 무효 문항, 채점 근거

이는 결과를 재현하고 실패 원인을 분리하기 위한 측정 메타데이터다.

**검증 수준: `C`**

### 8.2 왜 규준·백분위·진단을 만들지 않았는가

AERA/APA/NCME Standards는 사용 목적마다 타당도·신뢰도·공정성 근거를 수집하고, 근거 없는 해석과 오용을 막을 정보를 보고하도록 요구한다. 현재 후보 문항과 소규모 내부 자료만으로는 연령 규준, 절단점, 진단 정확도를 만들 수 없다.

따라서 현재 결과는 원점수, 오류 구성, 조건별 기술, 품질 상태만 보여 준다. 이것은 기능 부족이 아니라 타당하지 않은 해석을 막는 설계 결정이다.

**검증 수준: `A + C`**

### 8.3 왜 CAT를 아직 쓰지 않는가

컴퓨터 적응검사는 응답에 따라 다음 문항을 고르기 전에 문항은행의 난이도·변별도 등 모수가 충분한 표본으로 보정되어야 한다. 보정 오류를 무시하면 능력 추정도 편향될 수 있다. 현재는 검증된 한국어 문항은행과 IRT 모수가 없으므로 고정형 후보를 먼저 검증하는 것이 순서다.

**검증 수준: `A + C`**

## 10. 다음 연구에서 사전등록하거나 확정할 값

다음 값은 코드 상수로 존재하지만 연구 전 확정이 필요하다.

1. 연령별 시거리와 글자 크기 조건
2. 글꼴 후보와 굵기, 자간
3. TTS 음성 ID, 음원 버전, rate, 허용 SPM 범위
4. 350ms 제시 허용 오차와 세션 제외 규칙
5. ASR 모델 버전, 양자화, 장치, CER/WER 허용 기준
6. 채점자 훈련, 독립 채점 비율, κ 기준, 합의 절차
7. L0/L1/L2 동형 후보, 조건 순서, 분석 모형
8. 문항 제외, 결측, 재검사, 기기 실패 처리 규칙

이 값을 결과를 본 뒤 유리하게 바꾸지 않도록 파일럿 종료 후 본 연구 전에 고정한다.
